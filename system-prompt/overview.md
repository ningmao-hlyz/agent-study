# System Prompt 总纲

先读本篇建立框架，再读六份笔记看具体写法。本篇给结论，细节和例子在各篇笔记里。

## 一、先分清"提示词"包含哪几层

文件里常把它们连在一起，但来源不同：

| 层 | 承载什么 | 六家观察                                                                                               |
| --- | --- |--------------------------------------------------------------------------------------------------------|
| system / developer 消息 | 身份、行为规则、能力清单 | Pi、Hermes、Grok 是单个 system 块；Claude Code 为四个 Block；Codex 为六个 developer Block              |
| 工具描述与 schema | 具体参数约定、调用前置条件 | Claude Code 31 个、Pi 4 个、Grok 26 个、Hermes 24 个顶层小节；Codex 把多数能力包在 `functions.exec` 里 |
| 注入的 user 消息 | 环境、用户自定义规则、系统提醒 | Grok 把 `user_info` / `user_rules` 放在 user 消息里；DSH 的运行时上下文也在 user 消息内                |
| 运行时上下文 | cwd、平台、权限模式、模型声明 | 六家都有，且多为"当前值"而非"产品能力"                                                                 |

**要点**：消息角色由 API 定义，文件里的 `## Block`、`<tools>`、`<system-reminder>` 只是导出器的分组标签。**行为规则大量寄生在工具描述里**，因此只看 system 块会漏掉一半设计。

本主题把工具描述算在内，但必须标注上表的层级：说"某规则出现"时要说明它在哪一层；说"某 Agent 没有某能力"时不能只看顶层工具数（Codex 是包装入口，Hermes 和 Grok 还有动态加载的延迟工具）。

## 二、System Prompt 的八个组成模块

按模块读比按产品读更容易看出规律。

| 模块 | 它解决的问题 | 可对照的笔记 |
| --- | --- | --- |
| 1. 身份与目标 | 我是谁；把用户输入当请求还是动作；用什么态度与用户相处 | [Codex](codex.md)、[Grok](grok.md) |
| 2. 工具语义 | schema 表达不了跨字段匹配与执行顺序，必须用文字补 | [Pi](pi.md)、[Claude Code](claude-code.md)、[Hermes](hermes.md) |
| 3. 行为规则 | 何时推进、何时停、何时提问 | [Codex](codex.md)、[Grok](grok.md) |
| 4. 环境与运行时 | 平台、渠道、权限模式决定交付方式 | [Hermes](hermes.md)、[DSH](deepseek-harness.md) |
| 5. 安全与授权表述 | 把"能不能做"与"该不该做"分开 | [Grok](grok.md)、[Claude Code](claude-code.md) |
| 6. 记忆与状态条款 | 提示词里声明知识的归属与边界 | [Claude Code](claude-code.md)、[Hermes](hermes.md) |
| 7. 条件性段落 | 一份提示词适配多种模式 | [Claude Code](claude-code.md)、[Codex](codex.md) |
| 8. 布局与顺序 | 稳定性、缓存复用、重要性分配 | [Claude Code](claude-code.md) |

第 5、6 模块这里只看**提示词怎么表述**；机制实现（沙箱、授权、记忆存取）留待后续主题。

## 三、可复用的八条写法

1. **规则跟着接口走。** Pi 用 `edits[]` 批量匹配原文件，于是专门解释"匹配原文件、区域不重叠"；Claude Code 用 `old_string` / `new_string`，于是强调"先 Read、去掉行号前缀、`replace_all`"；Hermes 用模糊匹配，于是列出 9 种策略。接口不同，文字必须不同。
2. **把"何时问、何时做"写成可判定的条件**，而不是形容词。Grok 按"可逆性 + 影响对象"分档；Codex 按"是否已有授权"；Claude Code 给"难以撤销或外向动作"加确认条件。
3. **区分能力、配置、授权三层。** Codex 的 `exec_command` schema 仍列着 `require_escalated`，但当前是 read-only + `never`；字段存在只说明接口能力。写提示词时三层要分别表述。
4. **环境信息写"当前值"，不要写成产品属性。** Hermes 这次是 plain terminal（不渲染 Markdown、无附件通道），DSH 这次是 Web GUI（present 文件卡片），Codex 这次是 read-only。
5. **用条件段落，不要用互斥的绝对句。** Claude Code 的"专用工具优先"与"auto mode 下允许 Bash 读文件"是两段带条件的规则，扁平化成一句就失真。
6. **关键规则允许重复，但要有分工。** Pi 的编辑语义同时出现在系统规则和工具说明：系统区负责选工作流，工具区负责构造参数。重复会增加上下文开销，是否值得要看实现说明，不能默认有效。
7. **稳定性决定布局。** 变化频繁的内容（时间戳、环境）放后段；稳定前缀才有复用价值。缓存标记不等于命中，要看响应 `usage`。
8. **外部内容与指令要分层。** Claude Code 的 `<pasted_content>`、Hermes 的 OUT-OF-BAND 标记、DSH 的 `web_fetch` 都要求把"外部材料里的指令"排除在执行之外，并说明标签字符串本身不等于鉴权。

## 四、怎么读一份提示词

1. 看身份与目标 → 2. 扫行为规则的触发条件 → 3. 读工具描述里的隐含规则 → 4. 找条件性段落并确认是否生效 → 5. 最后看环境与布局。

每条规则问三句话：**它防止什么错误？为什么放这一层？代价是什么？**

## 五、边界

- 本轮只学 System Prompt 怎么写。记忆机制、上下文压缩、沙箱、权限、委派调度各自留给后续主题，这里只记录它们在提示词里的表述方式。
- 对比的是**文本与接口设计**，不是产品性能。
- 提示词长短不代表效果。验证一条规则要固定模型、工具与任务，只改这一条规则。
