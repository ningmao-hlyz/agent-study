# Pi 0.87.1：工具语义如何写进提示词

背景：版本 `0.87.1` / `default`，4 个工具，采集模型 `gpt-4.1`。原文见 [example/e-pi.md](example/e-pi.md)。

## 结论

1. **Pi 的编辑规则是接口的说明书，不是风格偏好。** `edit` 接收 `path` 加 `edits[]`，一次调用的多处区域**共同匹配同一个原文件**、要求唯一且不重叠。schema 表达不了"跨字段共同匹配"和执行顺序，只能用文字补。
2. **同一编辑语义在系统规则和工具说明里各出现一次**，分工不同：系统区帮你选工作流（精确改动用 edit、新建或整体重写用 write），工具区帮你构造具体参数。
3. Pi 的提示词很短，规则密度集中在工具分工上——篇幅小不等于设计简单。

## 这份提示词的层级

| 层 | 内容 |
| --- | --- |
| system 消息 | 编程助手定位、`<tools>` 概览、`<rules>` 操作规则、Pi 文档指引、工作目录 |
| 用户消息 | 采集用的输入，不属于 system |
| 工具定义 | `read`、`bash`、`edit`、`write` 四个独立接口 |

## 设计要点

### 编辑接口决定编辑规则

假想一次调用：原文件要把 `first = 1` 改成 `first = 2`，`second = 1` 改成 `second = 2`。如果模型把第二条的 oldText 写成含 `first = 2` 的片段，就依赖"第一条已经生效"——而在"所有编辑都匹配原文件"的接口下这个假设不成立，参数直接失效。

所以"匹配原文件、唯一、不重叠"这条规则的作用是**帮模型构造出工具能接受的参数**，而不是在描述一种编码审美。另一类失败同样由接口决定：大段匹配里包含重复或互相重叠的内容时，即使目标清楚，参数仍然无效。

### 规则重复的两种可能解释

系统规则与工具说明都写了编辑语义。可能的分工是"前者选工作流、后者构参数"；也可能只是文档生成复用了同一段描述，作者并未验证重复的收益。

## 可借鉴与代价

| 做法 | 收益 | 代价 |
| --- | --- | --- |
| 明确"原文件匹配"语义 | 减少依赖前序编辑的参数错误 | 增加模型理解与构参数的负担 |
| 唯一且不重叠 | 减少歧义与冲突 | 复杂重构可能需要重新划分编辑 |
| 系统区与工具区重复 | 提高关键规则被注意到的机会 | 增加上下文开销 |
