# Grok：意图分层、用户规则注入与验收流程

背景：一个 system Block + 三个 user 消息，3039 行、26 个顶层工具，另有动态 MCP。原文见 [example/e-grok.md](example/e-grok.md)。

## 结论

1. **规则出现在哪一层，比规则本身更重要。** Message 1 含 `user_info` 与 `user_rules`，其中既有肯定式表达偏好，也有 Web 浏览器验证流程，而且与顶部 system 规则**内容重复**。看到某条规则时必须记录它在 system 还是 user 层。
2. **按用户意图把工作分成动作 / 问答 / 审查三类**：只有明确动作请求才产生修改；问答与审查请求给回答，不做未要求的项目改动。
3. **把完成标准写成可执行的操作流程。** Web 改动要求像用户一样点击、输入、提交、导航，检查共享状态的关联页面，找回归与边界，并验证桌面与手机两种尺寸。
4. **事件唤醒要压缩。** `monitor` 要求 stdout 只输出 `DONE` / `FAILED` / `CANCELLED` 终态信号，因为每一行都会唤醒主 Agent。

## 顶部规则按职责组织

| 模块 | 主要内容 |
| --- | --- |
| 身份 | 自主完成软件工程请求，目标位于 `user_query` |
| dangerous_actions | 可逆的本地工作直接推进；破坏性、共享与外向动作有授权边界 |
| work_policy | 保留全部要求，按动作/问答/审查意图决定工作类型，真实报告 |
| background_tasks | 自有长任务后台运行；外部状态变化用 monitor |
| scratch_files | 自用临时材料默认放 `/tmp`，任务结束清理 |
| communication / formatting | 自包含、清晰简洁的回复与 Markdown 展示 |
| browser_verification | Web 改动后端到端操作、关联路由、回归与多尺寸验证 |

## 设计要点

### 用 XML 标签组织规则

Grok 的规则不是散文段落，而是一组自足的标签块：

| 标签 | 承载 |
| --- | --- |
| `<dangerous_actions>` | 可逆性判断与授权边界 |
| `<work_policy>` | 工作类型判定、保留全部要求、真实报告 |
| `<background_tasks>` | 后台任务与外部状态监视 |
| `<scratch_files>` | 临时文件位置与清理 |
| `<communication>` / `<formatting>` | 回复标准与 Markdown 展示 |
| `<browser_verification>` | Web 改动的端到端验收流程 |

注入内容同样用标签：`<user_info>`、`<rules>`（内嵌 `<user_rule>` / `<user_rules>`）、`<user_query>`。

好处是每块边界明确，便于按块增删、引用和裁剪。代价是**标签名不携带优先级**，顺序承担了重要性分配；而且 `<user_rules>` 嵌在 `<rules>` 之内，意味着用户规则被放进规则体系内部而不是并列在外——**这一层关系只有看嵌套结构才读得出来**，标签名本身不会说。

对照另外两家：Claude Code 用四个 Block、Codex 用六个 developer Block，都是**按消息切块**；Grok 是在一个 system 消息内部用标签切块。切分方式不同，但都在回答同一个问题——怎么让模型知道"这几条属于同一件事"。

### 用户规则注入是横向比较的关键变量

Message 1 是 `user_info` 与 `user_rules`，Message 2 是工作流提醒，Message 3 的 `user_query` 是采集输入。顶部 system 与 `user_rules` 有重复内容。

因此：观察到某条规则时，要记录层级；**不能把用户定制全部算作厂商默认策略**。`user_query`、`system-reminder` 只是区段标记，不自行改变消息角色。

### 按意图分层，而不是按"要不要动手"

开头写"没有 human operator"，但正文仍允许并要求必要确认，还提供 `ask_user_question`。**不能把"无操作员"读成"没有用户、不能提问或获得无限外发授权"。**

示例：问"为什么登录失败"与说"请修复登录失败"，后者才产生修改许可。

### 授权边界看可逆性与影响对象

明确请求的可逆本地工作可直接做；删除、`force push`、合并发布、共享数据权限、向别人发消息要检查明确授权。**此前批准、可用工具、自动权限批准都不为无关行为提供授权。**

这是三件事的区分：动作执行能力 / 工具层许可 / 用户意图授权。执行层自动放行不代表用户希望执行它。

### 把完成标准写成操作流程

browser_verification 要求改动 UI、布局、样式、路由、客户端状态或渲染数据后，在浏览器工具可用时完成实际验证：点击、输入、提交、导航；检查共享状态或组件的**关联页面**；找回归与边界状态；布局变化检查桌面与手机尺寸；发现问题后修复并重新验证。

例：改购物车写入逻辑，当前页面显示正常不够，还要看结算页等读取同一状态的位置。**截图证明画面，不独立证明交互与状态正确。**

工具不可用时允许最接近的替代验证并报告未覆盖项。这条规则针对"只在单页正常"的缺陷。

### 事件唤醒要压缩

`run_terminal_command` 支持 `block_until_ms`：为 0 时立即后台，前台超过等待阈值也转后台并返回 task id。`monitor` 用于观察外部状态，只发终态信号，必要失败立即通知、不等无关任务。

对照 Claude Code 的 Monitor 可发多种有用事件，这里明显压缩唤醒事件：省上下文与通知噪声，代价是细粒度进度可见性下降。

### 编辑语义对照：行号前缀

`search_replace` 是精确匹配：`old_string` 唯一，或开启 `replace_all`；匹配时**剔除 `read_file` 的行号前缀**；空 `old_string` 可用于创建新文件。`write` 覆盖已有路径前要求 `read_file`。

这里出现了第三种接口形态，也解释了一条通用规则：**"先读"不只为了安全，还因为读取结果的行号会污染后续匹配。**
